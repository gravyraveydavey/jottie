# Directory integration, Trash and native settings

## BambooHR

Settings → Integrations contains calendar selection and BambooHR. Enter the company subdomain or `https://company.bamboohr.com` address plus an API key, then choose **Sync directory**. An API key alone cannot identify the company endpoint: [BambooHR authentication](https://documentation.bamboohr.com/docs/getting-started) requires both. The key's user permissions and published-directory configuration determine which employees and fields are returned by the [directory endpoint](https://documentation.bamboohr.com/reference/get-employees-directory).

Only employee ID, display name, work email and job title are retained. The key goes into a Jottie-specific, per-company Keychain item; it is never written to settings, the database, transcripts, prompts or logs. HTTPS requests go only to the validated company host, with redirects disabled. No meeting content is sent to BambooHR. The first successful manual sync enables enrichment. Subsequent refreshes occur daily while the capture application is running, with a one-hour delay between failed background attempts. Failed requests leave the previous complete cache intact; manual Sync retries immediately. There is no background network access before an explicit connection.

`directory.sqlite` is a durable local cache separate from `search.sqlite`, with transactional replacement and a last-success timestamp. A newly connected company replaces the old directory. Disconnect removes that company's key and clears the cache. Old meeting analysis snapshots remain historical content; disconnect does not rewrite them.

Opening Settings can load the directory from several independent connections. Existing schema checks are read-only: repeating a schema-creation write transaction could fail at `COMMIT TRANSACTION` while another connection was reading. Connections now wait up to five seconds for transient contention during actual writes. Regression tests cover opening alongside a held read transaction, overlapping directory loads and concurrent alias updates, using synthetic directories.

New recordings preserve calendar invitee names and email addresses. Exact email matching takes priority. Without an email, only one unique normalised full-name match qualifies. Ambiguous names and conflicting emails remain unresolved; there is no fuzzy match or global employee dump in analysis. Each matched invitee carries company, employee ID, match method and directory sync timestamp. Only those invitees' directory context reaches opted-in Codex analysis. Invitations never establish attendance, identity of a speaker channel or commitments. The Speakers view displays these unconfirmed invitee matches separately from manual speaker corrections. Existing summaries are enriched only when explicitly regenerated.

The published directory may omit job titles or work emails; Jottie leaves absent values blank rather than requesting broader HR records. No salary, personal email, phone, address or other HR fields are cached. Live authentication and directory access require the user's company address and key entered in the application; automated checks use invented directories and request/response fixtures.

## Trash

Trash appears below Queue. Moving a meeting retains its complete canonical bundle and revision history, with a durable timestamp. Restore keeps the stable meeting ID and manual filing; if its folder was deleted, it returns unfiled. Empty Trash asks for confirmation and permanently removes local bundles. Otherwise items expire after 48 hours and are purged on launch and while Jottie runs. Nothing runs while the app is closed; overdue items are removed on the next launch.

Untimestamped Trash from older builds receives a fresh 48-hour grace period on discovery. A durable source-ID deletion record prevents automatic capture imports from resurrecting trashed or expired records. Restoring clears that record. Search rebuilds never index Trash. Published remote copies, publication receipts, imported original documents and original capture directories are preserved. The Trash action removes Jottie's library copy, not an external source document.

## Settings migration

The main window now opens General first, followed by Summaries, Recording, Integrations, Microsoft and MCP. Recording includes microphone/calendar permissions, the system-audio tone test, login registration/removal, speech-model download/repair/deletion, recording root, automatic recording rules and delays, app inclusion/exclusion, system/microphone audio settings, local engine/language/model controls, echo filtering, calendar/naming options, interface language, Dock/menu-bar/launch visibility and the after-session hook. Capture controls save individually; fields requiring restart are labelled. Permission and model actions use the existing engine APIs, and `Config.update` continues to drive the shared runtime settings applier.

The production settings path no longer opens the legacy settings window. The separate first-run setup assistant and legacy form remain for first-run onboarding and inherited test coverage. Cloud transcription/provider/key controls, retained-audio and upstream telemetry controls remain disabled by Jottie's privacy policy. Inherited summary-provider settings are replaced by native Codex model/effort and prompt controls. They are deliberately not reintroduced as inactive or misleading settings. Library-only CLI windows show that capture controls require the full capture app.
